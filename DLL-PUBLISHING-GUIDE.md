# ShaderOS — DLL-Only Publishing Guide

Internal engineering reference. This file is not part of the shipped package — it stays in the source repository only, alongside `RELEASE_CHECKLIST.md`-style documents for other products.

ShaderOS is confirmed Proprietary — private source repository, Binary Only Code Visibility. This guide's process has already been run successfully once, producing the 1.0.0 Asset Store package.

## What ships vs. what doesn't

Two assemblies exist today:

| Assembly | Current platform scope | Ships as |
|---|---|---|
| `ToolsStudio.ShaderOS` (Runtime) | Editor only | Compiled DLL |
| `ToolsStudio.ShaderOS.Editor` | Editor only | Compiled DLL |
| `ToolsStudio.ShaderOS.Tests.Editor` | Editor only, test-only | **Never ships** — dev-only, excluded from every export. Not currently present in this repository; the `InternalsVisibleTo` grant below is left in place for when tests are added |

The `Tests/` folder, all `.cs` source files, and both `.asmdef` files are development-repository content only. None of it is copied into the customer package.

## Step 1 — Produce the compiled assemblies

This step requires a real Unity Editor install with this project open; it can't be done from a headless shell.

1. Open the project in Unity (the version declared as the minimum supported — currently Unity 2021.3 LTS+).
2. Let Unity finish a full compile with zero errors and zero unaccounted-for warnings (see Publishing Readiness's Pre-Export Checklist for how to classify a warning).
3. Unity writes the compiled assemblies to `Library/ScriptAssemblies/ToolsStudio.ShaderOS.dll` and `Library/ScriptAssemblies/ToolsStudio.ShaderOS.Editor.dll` after every successful compile. These are the binaries to distribute — copy them out of `Library/`, don't rebuild them by hand.
4. Confirm both `.dll` files are present and current (delete `Library/ScriptAssemblies/` and let Unity recompile from scratch first, so there's no chance of copying a stale binary from an earlier state of the source).

## Step 2 — Assemble the binary-only package folder

Build this in a scratch location, never inside the working dev project:

```
Assets/
  ShaderOS/
    Runtime/
      ToolsStudio.ShaderOS.dll
    Editor/
      ToolsStudio.ShaderOS.Editor.dll
    Documentation/
      Getting Started.txt
      User Guide.txt
      Features.txt
      Troubleshooting.txt
      FAQ.txt
    README.txt
    CHANGELOG.txt
```

Delivery format is `.unitypackage`, not UPM — no `package.json` in this package. `README.txt`/`CHANGELOG.txt` and the `Documentation/` folder's five `.txt` files are the customer-facing plain-text equivalents of this repository's own `README.md`/`CHANGELOG.md` and the Documentation Repository's content — produced during export, never copied byte-for-byte.

No `Runtime/`, `Editor/`, `Tests/` source folders. No `.asmdef` files — a precompiled DLL doesn't need one. `.meta` files for the two `.dll`s are generated by Unity on import rather than hand-authored — see Step 3 for the Plugin Importer settings each needs.

## Step 3 — Set Plugin Importer settings on each DLL

Each `.dll`'s `.meta` needs its Plugin Importer platform settings set correctly, or Unity will try to include it somewhere it shouldn't:

- **`ToolsStudio.ShaderOS.Editor.dll`** — Select Platforms for plugin: **Editor only**. Uncheck every player platform.
- **`ToolsStudio.ShaderOS.dll`** — Same: **Editor only**, every player platform unchecked. This matches the asmdef fix already made in this pass (`includePlatforms: ["Editor"]`) and the product's own documented "Editor-only — no assemblies are added to player builds" claim. Getting this wrong is exactly how an Editor-only tool ends up silently adding weight to someone's player build.

Unity's own Editor UI is the only reliable way to set these — select the `.dll` in the Project window, go to the Inspector's Select Platforms for Plugin section, and configure it there. A hand-edited `.meta` risks a `PluginImporter` field mismatch Unity won't recover from cleanly.

## Step 4 — GUID stability

The `.dll.meta` files must carry **stable GUIDs across releases** once the binary-only package is live — any asset in a customer's scene that ends up referencing a type from these assemblies (unlikely for an Editor-only tool, but the Documentation folder's own GUIDs already follow this discipline per the earlier BuildLens fix) depends on this. Generate the GUIDs once, on the very first binary export, and never regenerate them on a later release — copy the same `.meta` files forward and only swap the `.dll` bytes inside them.

## Step 5 — Verify per Publishing Readiness's Import Verification

Per your own standard, this is checked through the actual delivery-format workflow, not assumed to work because it looks right:

- **If `.unitypackage`**: `Assets > Import Package` into a completely fresh project, confirm the menu item appears (`Tools/ShaderOS`, once the menu-path fix from the audit is applied), confirm a scan runs end to end, confirm zero Console errors.
- **If UPM**: add it to a fresh project's manifest the way a customer would, confirm it resolves and the window opens cleanly from that path.

## Known Follow-Up Work

A full member-by-member audit converting unnecessary `public` types to `internal` across the codebase has not been done. The `InternalsVisibleTo` grants in both `AssemblyInfo.cs` files exist specifically so this can be done in a future pass, inside a real Unity Editor where each change can be compiled and checked, without losing cross-assembly access to `ToolsStudio.ShaderOS.Editor` or a future `ToolsStudio.ShaderOS.Tests.Editor`.
